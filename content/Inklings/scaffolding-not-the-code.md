Last month, there was a lively Slack thread at work discussing what's becoming a common concern: the volume of AI-generated code is outpacing our ability to review it. The first instinct was a responsible one: stop creating new code until the backlog was sorted, rather than risk piling up PRs that created a false impression of "done." But I think it also presents an opportunity to revisit something more fundamental: whether the way we've been doing PR reviews has ever been the right quality mechanism in the first place.

What we call code review is, in practice, a human reading a diff and mentally simulating what the code does. We look for bugs, check for style, try to spot logic errors. But humans aren't good at this. Attention fades, confirmation bias kicks in, we pattern-match on "this looks fine" rather than rigorously verifying behaviour. Traditional PR review was a stopgap for insufficient automation, and when code volume was low, the gaps didn't compound into visible failures. AI didn't break code review so much as make the inadequacy impossible to ignore. Even having AI read the code isn't enough. Ramp Labs recently [wrote about](https://ramplabs.substack.com/p/self-maintaining) building an agentic system that monitors their production codebase. An early version that reviewed code statically, the way a human would, proved ineffective. Their key finding: "subtle failure modes are rarely apparent from static code review." What worked was having agents reproduce failures in sandboxed environments, making real API requests and running tests against live code. The verification has to be _behavioural_.

Building software still demands discipline, but the discipline shows up more in the scaffolding rather than the code. 
 								- [OpenAI blog post on harness engineering](https://openai.com/index/harness-engineering/#:~:text=building%20software%20still%20demands%20discipline%2C%20but%20the%20discipline%20shows%20up%20more%20in%20the%20scaffolding%20rather%20than%20the%20code.)
:::

This pattern isn't new. Manufacturing hit the same inflection when craft production gave way to mass production. A master craftsman making twenty chairs a week could inspect each one by eye and hand. When the factory made twenty thousand, inspection didn't scale. Quality had to become a property of the production system itself. The entire discipline of quality assurance and statistical process control emerged because scale forced the question: if inspection doesn't produce quality, what does? Software is arriving at that question now. The OpenAI harness engineering piece a while back put it this way: the discipline shows up "in the scaffolding rather than the code." The engineer's job becomes [[202604200704-platform-engineering|designing environments]], specifying intent, and building feedback loops, not reviewing diffs line by line. It's the difference between inspecting each output and building the system that makes correct output the default.

As part of an organization-wide re-architecting discussion, I had the thought that the team needs a "definition of good" and a vocabulary precise enough to reason with before re-architecture means anything. I've been reading about [[202604201021-evolutionary-architecture|evolutionary architecture]] for the past month or so, and the concept of _fitness functions_ gives this idea a concrete mechanism. A fitness function is a formalized, objective definition of what "good" means for a specific property of a system. Not "we want good performance," but "P95 latency under 200ms," or "every source column has a not-null test," or "no model has more than three upstream dependencies." Ramp's production monitors are fitness functions by another name, evaluated behaviourally against real state in sandboxed environments. And because fitness functions aren't a one-time gate but ongoing governance, they don't just help build a better system; they help preserve its qualities as it evolves. When each new pipeline or data source doesn't add proportional review burden, the marginal cost of delivery starts bending in the right direction.

Amongst the myriad of considerations and concerns as the re-architecting starts, I find myself circling three questions. First, what do we want this new architecture to _be_, not in terms of tools or frameworks, but in terms of the properties it must exhibit? Second, how will AI help us get there, and where might it work against us, given that volume without verification just accelerates drift? And finally, once we've built something new and hopefully better, how do we keep it that way as the system evolves? Rebecca Parsons, one of the co-authors of the evolutionary architecture concept, makes the [point](https://www.thoughtworks.com/insights/podcasts/technology-podcasts/how-fitness-functions-help-govern-measure-ai?utm_term=&gad_source=1&gad_campaignid=23432940674&gbraid=0AAAAAD3t1PLV73Scq4LQQ7Yxki3qQEOX5&gclid=EAIaIQobChMI6pKW78vAkwMVtjNECB3ByimpEAAYASAAEgI1QvD_BwE#Transcript:~:text=your%20target%20architecture%20is%20now%20the%20conceptual%20composition%20of%20all%20of%20your%20fitness%20functions%20because%20that%27s%20what%20you%27re%20trying%20to%20get%20the%20architecture%20to%20achieve.) that your target architecture is really the conceptual composition of all your fitness functions. I think that's right, and it reframes something about this period of "soul searching" for the organization, as the weight of the previous years of survival has become untenable on the technical infrastructure and staff. AI has made execution less of a constraint than it's ever been. What remains scarce is clarity about what we actually want: an educated imagination about what the system should do and be. If the architecture we build is the sum of the fitness functions we choose, then what we choose to measure is a statement about what we value.
