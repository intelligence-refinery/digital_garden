# Contextual Background

- The application is a data platform for customer insights
- Need to migrate a legacy mainframe to the cloud

# High-level view of Consumer Subsystem



- The application consists of two types of workloads connected by the database
	- Batch data pipelines that ingest and enrich data, writing them into the database
	- Online API layers generated by user interaction with platform that retrieve data from the database

# Incremental Legacy Displacement: Principles, Benefits, and Considerations

:::{.margin}

**Related concepts**
[[202604281018-dark-launching|Dark launching]]
[[202604281019-canary-release|Canary release]]

:::

- Success criteria
	- Outcome parity between the legacy and cloud-based system
	- Satisfy existing performance requirements
- Guiding principles
	- Fail-fast, to identify risks early
	- Delivery value early, in thin slices 
- Thus, opted for an "**Incremental Dual Run**" approach, where a [[202604262236-transitional-architecture|transitional architecture]] was used to support slice-by-slice displacement of capabilities away from a legacy system
	- So the legacy and new systems can run temporarily in parallel to deliver value and validate parity


# Incremental Legacy Displacement Approach

:::{.margin}

**Related concepts**
[[202604281123-vertical-slices|Vertical slices]]

:::

- Examples of components that could be migrated independently to the cloud in sequenced increments
	- Data curation vs data serving and product use
	- Datasets were managed largely independent of each other
		- So could do the cloud migration for any given dataset
		- "As long as up- and downstream dependencies could exchange data from the new cloud system, these workloads could be modernized independently of each other"
	- Subset of customers who had purchased a smaller percentage of capabilities and data, so the first increment is small and can be delivered more quickly
		- Subsequent increments would build on top of the prior work
